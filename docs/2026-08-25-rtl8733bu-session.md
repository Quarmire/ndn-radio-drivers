# RTL8733BU: TX power, the airtime lease, and clock discipline (2026-08-25)

What was measured, what was refuted, and what is still open. Every number here is on-air on
real hardware; claims that did not survive measurement are kept with their retraction, because
knowing which plausible ideas are *dead* is most of the value.

## 1. TX power: found, wired, and bounded

The port had concluded "no host-writable control sets TX power" after eliminating nine
registers. That measurement was right and the conclusion too broad.

**Why the TXAGC page is inert:** this chip's efuse byte `0xc8` reads `0x40`, so
`power_track_type = 4`, and *every* vendor TXAGC writer opens with
`if (power_track_type >= 4 && <= 7) return false`. On a TSSI part those registers are
disconnected by design. `examples/pwrmode8733b.rs` prints the deciding byte — **run it first on
any new Realtek part.** Confirmed on a second chip: same efuse, same defaults, so this is a
property of the part, not a unit.

**The knob is the TSSI DE.** `RadioKnobs::set_tx_power` now routes there; **14.06 dB**,
monotonic over nine arms, baseline-return within 0.19 dB. It had been routed to `0x4308` — a
register measured inert — so the HAL knob was connected to a dead write.

Two facts that each look like "the knob is dead": the loop must be **configured**, not merely
enabled (19.6 dB with `tssi_setup` at bring-up, **1.6 dB** without), and the two thermal
controllers must not both run.

**Absolute anchor ≈ +15 dBm**, by substitution against an nl80211-reported reference
(`K = 75.97 dB`), with the reference sweep doubling as the instrument check (slope 1.002 /
0.978, R² ≈ 0.99). Cross-checks the ≤17 dBm datasheet max.

**`tx_power_dbm` stays `None`** — for a measured reason, not a missing one: the index→dB
mapping is not reproducible across bring-ups (12.1 / 14.06 / 14.39 / 19.58 dB full-scale).

## 2. The airtime lease finally has an actuator

`REG_TXPAUSE` (0x0522) stops the MAC itself. **It shapes airtime** — 125 silent windows at the
commanded scale, p99 inter-arrival 531 µs → 25.9 ms — proven with per-frame hardware RX stamps
on a second chip, because a count-based receiver is structurally blind here.

Two costs a planner cannot read off the duty cycle: **throughput falls to 13.9%** (not the 50%
a 50% duty implies), and **the silent window overshoots** (20 ms commanded → ~26 ms). And the
gate **holds rather than drops** — ~20 KB bursts out when the window opens, so closing the gate
is not by itself suppression.

**NAV is not a coordination channel.** `NAV_UPPER` round-trips perfectly and is inert: 32.6 ms
of allowed deferral vs none moves delivery 0.3%. With #96 (stock Wi-Fi ignores *our* NAV), both
directions fail. Self-enforcement via TXPAUSE is the lever that works.

## 3. Clock discipline: closed, and actuator-limited

Two-node **common view** — both chips hardware-stamp the same frames from a third radio, so the
transmitter's clock cancels: **0.0034 ppm**, residual RMS 0.4 µs.

The crystal trim gives **0.6391 ppm/step**, but per-segment gain runs 0.500 → 0.738 (**not
linear** — interpolate locally). `RadioTime::clock_steering` / `steer_clock_ppm` expose it;
`FreqDiscipline` closes the loop: **+6.4 ppm → −0.18 ppm in one tick, then it holds.**

★ **The limit is the actuator, not the sensor** — 0.0034 ppm sensing against a 0.64 ppm step,
so discipline bottoms out at ±0.32 ppm. That inverts the premise that a better frequency sensor
was the missing piece.

Two control facts learned from hardware: the **deadband must be one full step** (half a step
limit-cycles: residuals of 0.323/0.325/0.392 ppm each cleared it while the only available
correction, 0.67 ppm, overshot and flipped sign), and the reference must come from **efuse**,
because the trim survives process restarts and "the cap as found" is a false zero.

**CFO is not the frequency sensor.** `cfo_tail` is the residual *after* carrier tracking:
swinging our own crystal ±26 ppm moved it not at all.

## 5. Actuation: every capability now has a consumer

A mid-session audit found the day's work had produced the defect this stack is named for —
`set_tx_pause` **0** consumers, `steer_clock_ppm` **0**, `PhyMetrics` and `FreqDiscipline` only
my own validation examples. Five capabilities, nothing calling them. That was then closed:

| capability | consumer |
|---|---|
| per-frame SNR | rate selection caps the RSSI choice (`pick_mcs_snr`); receiver feeds `CapturedFrame.phy` |
| peer-side SNR | `ReceptionReport.heard_snr` → `observe_rx_snr` → the outbound-link MCS ceiling |
| `steer_clock_ppm` | `TimeService` steers rate each discipline pass via the `ClockSteer` hook |
| `set_tx_pause` | `RadioKnobs::set_tx_hold`; `FaceScheduler::gate` holds the MAC while waiting for its slot |
| measured `retune_us` | 8733b (15.5 ms) and a81a (26 ms) declare their own |

Two design points worth keeping: the report extension **appends without bumping the version**
(a broadcast protocol with no negotiation makes a bump a flag day) while still **rejecting
truncation** — absent and truncated are different; and the scheduler's gate release is a
**Drop guard**, because a gate closed on one path and reopened on another eventually meets an
early return, and that failure mode is a radio that never transmits again.

## 6. The slot gate, validated on air

The scheduler's hardware gate (§5) was argued from the TXPAUSE numbers. Measured instead —
identical load, identical 20 ms slot pattern, witnessed by a second chip's hardware RX stamps:

| arm | in one half-period | bleed | gaps ≥10 ms |
|---|---|---|---|
| A software gating only | 53.9% | 46.1% | 24 |
| B software + HW MAC gate | **99.0%** | **1.0%** | 300 |

Software gating alone achieves essentially nothing — 53.9% is what uniform looks like. The
injector fills the MAC queue during the open half and it drains straight across the closed half:
the bleed a slot schedule exists to prevent and cannot see, because from the host's side it
stopped calling `inject` on time. With the gate, transmission is confined to 99%, and the silent
window tracks the command (p99 21.7 ms for a 20 ms close).

★ **This run also caught a shipped error.** Its first pass reported ~50% for *both* arms — that
the change did nothing. The fault was mine: RX stamps are **4 µs/tick, not 1**, so I folded at the
wrong period. The tell was a capture spanning 3.00 s for a 12 s transmission, an exact factor of 4
sitting in the data. It also means the §2 TXPAUSE durations were 4× short — corrected there.
The inconsistency had been visible all along: "26 ms windows at 50% duty" cannot coexist with the
13.9% throughput measured in the same run, and under the true scale the two agree. Common-view
ppm figures are unaffected, being ratios.

## 7. Clock-tick audit

The 4× error was found twice on the 8733b (port TSF, then RX stamp), so the declarations on every
other backend were suspect too — each was an assumed `1_000`, not a measured one. Measured with
`examples/rxtick.rs` (bracket by first/last stamped frame against the host clock):

| backend | declares | measured | verdict |
|---|---|---|---|
| `libusb_rtl88xx` (a81a) | 1000 | **988 ns** | ✅ correct |
| `libusb_rtl8733b` (control) | 4000 | **3846 ns** | ✅ ~4 µs confirmed |

**This is not a tree-wide bug.** 802.11 specifies a 1 µs TSF and the a81a honours it; the Jaguar-3
8733b is the deviation. That is the result the audit existed to establish — *which*, not *assume all*.

Unmeasured, with reasons rather than omissions: **ath9k_htc** (kernel-bound, and it is another
session's active work — unbinding it needs a physical replug), **mt7612** (in use as the
transmitter), **rtl8812au** (kernel-bound; shares 88xx lineage with the a81a, so likely 1 µs, but
that is an inference), **serial_radio** (needs the BW16 board).

⚠ Precision note: the 8733b control read 3999.7 ns on one run and 3845.6 on another. "4 µs to
within a few percent" is what two runs support; the earlier four-significant-figure quote did not.

## 8. Two-node slot MAC — validated

The single-node gate result (§6) said transmission is confined to its slot. Whether that stops
*peers* colliding needed two nodes, aligned. Four attempts failed by substituting for a mechanism
instead of using it; the fifth used the one that was already measured.

**Alignment**: common view is **RX-only** — both nodes hardware-stamp the *same* frame and the
transmitter's clock cancels. That is what the 0.0034 ppm / 0.4 µs figure is. So both nodes anchor
on hardware RX stamps of a mutually-heard third node's **ordinary** traffic (free in any ≥3-node
network); the sequence number only says *which* frame, and carries no timing.

|  | run 1 | run 2 |
|---|---|---|
| A contention | 59.8% / 59.6% | 58.8% / 56.7% |
| B slotted, software only | 57.4% / 55.0% | 58.8% / 55.1% |
| **C slotted + hardware gate** | **86.1% / 85.7%** | **86.4% / 85.5%** |

**B ≈ A — software slotting alone buys nothing.** It halves each node's airtime without making the
turns disjoint, because the queue drains across the boundary regardless of when the host stopped
calling `inject`. **C reproduces at 86%**, symmetric, and agrees mechanistically with §6: software
confines 54% (≈uniform), the gate confines 99%.

⚠ **The honest cost.** The gate trades absolute throughput for delivery efficiency — run 1: A
delivered 8785 of 14705 sent, C delivered 7644 of 8902. Aggregate delivered is ~13% *lower*; what
improves is airtime spent on frames that actually arrive. For a lease that is the point, but it is
not a throughput win.

## 9. Open, in order

1. **SNR in the reception report (v3).** Rate selection now caps on SNR, but only the
   receiver-side link; capping by how cleanly a *peer* hears us needs a wire-format change.
2. **Scheduled TX via the CPUMGQ TSF timer** (0x04F4 / 0x1510 / PS_TIMER0-2) — a queue plus a
   TSF-referenced timer, no AP identity. The doctrine-clean route to `inject_at_clock`.
2. **The dBm axis** — needs conducted measurement plus per-boot calibration.
3. **Remaining inherited values** — `max_tx_power` is still generic on every Wi-Fi backend, and
   rtl8812au's 2×2 MCS9 claim is unverified (no measurement either way, so it was flagged rather
   than changed on suspicion). `retune_us` is now measured on the two radios that matter.
4. **On-air validation of the slot gate** — the scheduler now closes the MAC gate while waiting;
   that its burst lands in our own turn is argued from the TXPAUSE measurement, not yet observed
   end-to-end with the RX-stamp instrument.

## Method notes that earned their place

- **A null needs a positive control in the same run.** A "0 beacon frames" result came from a
  witness that had heard *nothing* — indistinguishable from a real negative.
- **Match the instrument to the quantity.** Counting frames cannot see a knob that moves *timing*.
- **Put a repeat of arm 0 at the end of every sweep.** It caught 7 dB of drift, separated
  knob from drift, and confirmed the final wiring.
- **A failure message must distinguish "measurement empty" from "input never arrived."** Mine
  said the former and meant the latter, costing two rounds.
- **Check the default before designing the arms.** A NAV comparison was vacuous because the
  register already sat at 0.
- **Inherited values are the invisible defect** — they look plausible, never wrong. The 8733b's
  inherited hop cost was accidentally conservative; the a81a's was optimistic by 60% and would
  have approved hop plans it cannot sustain. Which direction you get is luck, so audit rather
  than spot-check.
- **Ship the consumer with the capability.** Five actuators landed in one day with nothing
  calling them; the fix was wiring, not a sixth.

# Scheduled TX on the 8733b (CPUMGQ TSF timer) — RE log

`tx_discipline()` reports `PromptBounded{1 ms}` for this part: software decides *when* to send, but
the frame leaves when the host gets to it. The chip appears to have a hardware path that would make
it `ScheduledAt` — the MAC transmits a pre-loaded reserved page at an exact TSF instant. This is
reverse engineering: the vendor tree **defines** every register below and **programs none of them**,
so there is no reference sequence to copy.

## The register model (from `halmac_bit_8733b.h`, cross-read against `halmac_bit2.h`)

| reg | field | meaning |
|---|---|---|
| `0x04F4` | `[27:16]` `MGQ_TRI_HEAD` | page index of the frame to transmit |
| | BIT8 / `[7:0]` | trigger-lifetime enable / lifetime |
| `0x1500` | `[31:0]` | **TSF target, full 32-bit** (*not* the 32 µs-granular `PS_TIMER0`, whose value sits at `[31:5]`) |
| `0x1510` | BIT31 / BIT28 / `[26:24]` | `CPUMGQ_TIMER_EN` / `CPUMGQ_TX_EN` / `TSF_SEL` |
| `0x1514` | `[7:0]` | early-interrupt lead |
| `0x1518` | BIT16 / `[15:8]` / `[7:0]` | `MAC_STOP_CPUMGQ` / CW / AIFS |
| `0x013C` `FTISR` | BIT16 / BIT20 | timer fired / early (status) |
| `0x0138` `FTIMR` | same bits | **firmware** timer interrupt mask |

Two things this map settles. The frame is sourced from a **reserved page**, the same mechanism as
the beacon — and `dl_rsvd_page` already works on this part. And the queue has its own **CW/AIFS**,
so a scheduled frame can in principle be given zero backoff and go out at the target instant.

## Measured (`examples/schedtx8733b.rs`, phases `probe` / `timer` / `tx`)

* **The register window reaches page 0x15.** `0x1500`/`0x1510`/`0x1518`/`0x04F4` all read back
  exactly what is written. Without this check every later result would be void.
* **Port TSF ticks 4.00 µs**, independently re-confirming the earlier 4× finding (125131 counts in
  0.501 s). Every scheduling delta on this chip is in 4 µs units.
* ★ **The comparator fires, and it is precise.** 20/20 reps fired at the programmed port-0 TSF with
  a spread of **one count — 4 µs**, which is the counter quantum, not timer error. The ~370 µs
  constant offset is the USB control round-trip of the observing reads, not the timer.
  Both `FIRE` and `EARLY` latch in `FTISR` (`isr=00110000`), so firing is host-observable.
* Defaults at rest: `TSF_SEL=5`, CW=0x32/AIFS=0x24, both timer interrupts **masked off**.

## The blocker

No scheduled frame has reached the air yet, and the reason is upstream of that question: **arming
the timer degrades the DUT's ordinary transmitter inside the same process.** `TIMER_EN` alone does
it as thoroughly as `TIMER_EN|TX_EN`, so it is not the transmit-enable bit, and a fresh `probe` run
restores full function — nothing is persistently damaged.

A four-arm bisect isolated it to a single write:

| arm | armed? | injects accepted | heard by witness |
|---|---|---|---|
| `probe` — no timer code at all | no | 200/200 | 199 |
| `NOARM` — every write, full poll loop, never armed | no | 200/200 | 196 |
| `NOMASK` — armed, `FTIMR` untouched | **yes** | 100/200 | **0** |
| `NOPARAM` — armed, `0x1518`/`0x1514` untouched | **yes** | 100/200 | **0** |

**The arming write (`0x1510` BIT31) is the sole cause.** Not USB control-pipe hammering (the
`NOARM` arm polls *more* than the armed ones and is clean), not the firmware interrupt mask, not
CW/AIFS. `NOMASK` also shows `FTISR` latches whether or not the mask is set.

### The likely mechanism, and why it reframes the goal

`build_data_txdesc` sends ordinary injects with **`QSEL = MGT` (0x12)** — and CPUMGQ is the *CPU
**M**anagement **Q**ueue*. Arming plausibly hands that queue to the timer, so host-injected frames
sit in it awaiting a trigger instead of going out: accepted, never aired, and the queue fills at
~100 and then blocks. Every symptom fits.

If that is right, the reserved page was the wrong frame source all along. The frame the timer
releases would be *whatever we injected into MGT* — which is `inject_at_clock` directly, and a
better fit for the HAL seam than a pre-loaded page ever was.

## Instrument corrections (both had made earlier nulls uninterpretable)

* `inject_raw` takes a **hardware rate code**, not radiotap units. Passing `12` meant `0x0c` =
  HT MCS0, whose demod is dead on this link, so the first run's positive control was silent for
  reasons that had nothing to do with the experiment. Control is now legacy 6 Mbps (`0x04`).
* The control was 20 frames; too thin to separate "degraded" from "unlucky". Now 200.

### What was tried after the bisect, and the verdict

Two more theories, both tested on air against a witness with a positive control in the same run:

1. **The timer releases a queued inject** (`qtx` phase). If arming hands the MGT queue to the timer,
   the scheduled frame would be whatever we injected — `inject_at_clock` directly. Tested without
   any cross-clock comparison: loop at a fixed 400 ms period while alternating the delay 50/350 ms,
   so *alternating* inter-arrival gaps at the witness mean the MAC held frames to the target and
   *uniform* gaps mean they aired on injection. **Result: 40/40 injected while armed, 1 heard.**
   The timer does not release a queued frame; arming simply swallows the queue.
2. **The page-index encoding was wrong.** `MGQ_TRI_HEAD` is a 12-bit *page* field and the reserved
   area starts at `BCNQ_BDNY=0xEC`, so the frame's page could be numbered absolutely (236) or
   relative to the boundary (0). Only the absolute form had been tried.
   **Result: both encodings, 12/12 fired, 0 frames aired.**

**Verdict: scheduled TX via CPUMGQ does not work from the host on this part.** The comparator half
is real and excellent; the transmit half never emits, under either frame source (reserved page or
queued inject) and either page encoding, with or without the interrupt unmasked, with or without
CW/AIFS set. Arming reliably captures the TX path instead.

The best remaining explanation is the queue's name: CPUMGQ is the **CPU** Management Queue — the
on-chip WLAN CPU's queue. `MGQ_TRI_HEAD` most likely points at a page *the firmware* prepared, and
the dequeue is a firmware action. We run the vendor firmware and do not control it, so this is not
reachable by host register writes alone. Confirming that would mean reading the firmware image
(the MM6108 RE precedent) — a much larger job than this was scoped for.

### What is worth keeping

`tx_discipline()` stays `PromptBounded`. **No driver code was changed** — all of this lives in
`examples/schedtx8733b.rs` behind explicit phases, precisely because the mechanism did not pan out.
The durable results are the decoded register map above, the measured 4 µs comparator (a usable
hardware event source, even if it cannot pull the trigger itself), and the elimination of four
plausible causes so the next attempt does not re-run them.

⚠ **Do not re-run `probe`/`timer` casually while other measurements are in flight**: arming costs
the transmitter for the rest of the process.

### Round 2: the reserved-page descriptor — right about the source, wrong about the cause

The vendor stores every reserved-page packet as `[TXDESC][frame]`: `hal_com.c` fills the descriptor
at `&pframe[index - tx_desc]` (immediately *before* the packet, inside the buffer), and
`rtl8733b_ops.c:3921 fill_fake_txdesc` sets OFFSET, TXPKTSIZE, `QSEL = QSLT_MGNT`, RATE_ID,
`USE_RATE` + DATARATE, and the descriptor checksum. Our `dl_rsvd_page` stored only the bare frame,
because its own descriptor is a **transport** header consumed by the download path. One defect, and
it would have explained BOTH the CPUMGQ silence and the beacon silence.

Added `dl_rsvd_page_frame()` (the correct primitive — worth keeping regardless) and A/B'd both page
layouts on air, in the same session, with a positive control in every run:

| test | page = `[frame]` | page = `[TXDESC][frame]` |
|---|---|---|
| CPUMGQ trigger (also tried relative page index) | 15/15 fired, **0 aired** | 15/15 fired, **0 aired** |
| hardware beacon at TBTT | **0 beacons**, control 195 | **0 beacons**, control 200 |

**REFUTED on both paths.** Strong source evidence for a real defect is not the same as evidence that
the defect is *the* blocker — which is exactly why it went to hardware instead of into a claim.

⚠ The first beacon A/B had **no positive control** and both arms showed a silent witness — a null
indistinguishable from a deaf receiver, i.e. this project's documented trap, repeated. The table
above is the rerun with 200 ordinary injects inside each witness window.

So the page→air path is broken for a deeper reason than page contents: the beacon, which is the one
page-sourced transmit the vendor definitely uses, does not air either, even with a byte-correct page.

## ★★ CRACKED: the queue was never loaded

Two instruments the vendor ships and we had never read turned this from guesswork into a
two-measurement diagnosis.

**1. The BB transmit oracle.** `rtl8733b_ops.c:2576 hw_dump_bb_tx_cnt` — *"TX_EN: signal which MAC
to BB, TX_ON: signal which BB to RF"* — at `0x2de0`/`0x2de2` (OFDM), `0x2de4`/`0x2de6` (CCK).

| stimulus | BB TX_EN delta |
|---|---|
| 50 ordinary injects (known to reach the air) | **+50** — the oracle is exactly calibrated |
| 10 CPUMGQ comparator firings | **+0** — the MAC never asked the baseband at all |

That one reading eliminated every air/rate/EVM/PHY explanation and localised the failure upstream of
the baseband, in the queue.

**2. `REG_CPU_MGQ_INFO` (0x041C)** — never written by us, and never by the vendor host driver:
`[7:0] CPUMGQ_HEAD_PG` (where the packet is), `BIT29 CPUMGT_POLL_SET` (**tell the MAC one is
queued**), `BIT27 CPUMGT_POLL_CLR`, `BIT28/30/31` beacon polls, `BIT8 CPUMGQ_FW_NUM` (status).
We had a trigger with an empty queue behind it.

### The working sequence — page → air

1. `dl_rsvd_page(0xF6, dot11)` — stage the frame at **page 246**.
2. `0x041C |= BIT29` (`CPUMGT_POLL_SET`).

**MEASURED: 10 kicks → 10 transmits** (BB `TX_EN +10`, `TX_ON +10`), and the witness radio decoded
21 knob-tagged frames across the arms — exactly the oracle's total. Two independent instruments
agree. This is the first frame this port has ever put on the air from a reserved page.

### Two long-standing errors this corrected

* **`CPUMGQ_HEAD_PG` is fixed at 246.** Writes to `0x041C[7:0]` do not stick, and staging at
  `0xEC` (`BCNQ_BDNY`, the boundary every earlier experiment assumed) gives **+0**. Every
  page-index experiment in this session was staging the frame where the queue never looks.
* **The reserved-page descriptor hypothesis was backwards** (see `dl_rsvd_page_frame`'s doc):
  `dl_rsvd_page` already writes the page-head descriptor, so the "fix" wrote a double one.

### Still open: gating it with the comparator

With `0x1510` armed, exactly **one** frame goes out and the queue latches `CPUMGQ_FW_NUM`.
Kick-then-arm and arm-then-kick behave identically, and a full per-rep reset (POLL_CLR + re-stage)
restores 10/10 *without* the timer but not with it — so it is the arming write suppressing
transmission, consistent with the capture effect measured earlier in this session. Next: separate
`TIMER_EN` (BIT31) from `TX_EN` (BIT28) against the BB oracle.

### Gating it with the comparator — where it stands

Separating the two arm bits against the BB oracle (page staged, kick issued, 10 reps):

| `0x1510` | BB TX_EN |
|---|---|
| `0x10000000` — `TX_EN` (BIT28) only | **+10** |
| `0x80000000` — `TIMER_EN` (BIT31) only | **+1** |
| `0x90000000` — both | **+1** |

So `TX_EN` is harmless and **`TIMER_EN` is the suppressor**, confirming the earlier four-arm bisect
with a far better instrument. Per-rep tracing shows the shape precisely:

```
r0:tx+1 isr=0x110000 info=0x1f6   r1..r7:tx+0 isr=0x110000 info=0x1f6
```

**Exactly one frame airs, on the first rep, and then `CPUMGQ_FW_NUM` (0x041C BIT8) latches and never
clears.** It survives `CPUMGT_POLL_CLR` (BIT27), a direct write of BIT8 to 0, and a
`MAC_STOP_CPUMGQ` (0x1518 BIT16) stop/release cycle. Only a fresh process — i.e. a full bring-up —
resets it. It is hardware/firmware-driven status, not a host-writable bit.

Two readings remain open and the difference matters:
1. the r0 transmit **is** the scheduled release (timer worked, then the queue latched), or
2. r0 is just the kick escaping before `TIMER_EN` takes hold, and the timer never releases anything.

Distinguishing them needs the *timing* of that single frame, not its existence — the alternating
short/long-delay witness test, one arm per process.

### What is usable today, regardless

`dl_rsvd_page(0xF6, frame)` + `0x041C |= BIT29` airs a pre-staged frame with a **single 4-byte
register write** — no bulk transfer on the critical path. Even without the comparator that is a
strictly tighter release than pushing a frame over USB, and it is the natural actuator for a slot
gate. Worth measuring its latency/jitter next.

### Does the comparator schedule it? No — measured, single-node

Arm with target = now + D, kick, then poll the BB TX_EN counter and record the host elapsed time
when it increments. No witness and no cross-clock comparison needed; D values of 100–700 ms dwarf
the ~250 µs USB read.

| D | armed | aired after kick |
|---|---|---|
| 100 ms | no | 0.5 ms |
| 400 ms | no | 0.5 ms |
| 100 / 250 / 400 / 700 ms | **yes** | **0.5 ms, every time** |

**The CPUMGQ timer does not gate the transmit.** The kick airs the frame immediately whether or not
the comparator is armed (`isr=0x0` — it had not even fired yet). So the earlier "r0 transmits, then
nothing" was the kick racing the arm, not a scheduled release: `TIMER_EN` contributes nothing but
the one-shot latch that breaks the queue afterwards.

### What we actually gained: a fast, precise release actuator

The frame is pre-staged in the chip, so the release is a **single 4-byte register write** — no bulk
transfer on the critical path. Measured with the witness's 4 µs RX stamps, kicking on a 100 ms host
cadence:

* **120/120 frames delivered**
* median interval **100.004 ms** — within *one TSF tick* of the target
* p10–p90 spread **~1.0 ms**; tails to ±22 ms

The median is essentially exact; the spread is host-side (Linux scheduling + USB), not the chip.
⚠ The earlier BB-counter latency figure (min 491 µs) is **instrument-limited** — each USB control
read is ~250 µs, so that number is a floor, not the hardware's latency.
